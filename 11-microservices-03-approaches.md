# Домашнее задание к занятию «Микросервисы: подходы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.


## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

--------------------------------

Я считаю лучшим вариантом исплоьзовать GitLab. Идеально подходит для этих требований, и лучшая часть всего этого - облачная версия не требует поддержки собственной инфраструктуры для самой платформы, при этом позволяет подключать собственные раннеры.

Требования:

- Облачная система и Git: GitLab.com или self-managed в облаке. Репозиторий на каждый микросервис — стандартная практика, GitLab Groups позволяют держать их вместе, но с отдельными правами и пайплайнами .

- Запуск сборки по событию из SCM: триггеры on push, on merge request в .gitlab-ci.yml.

- Запуск по кнопке с параметрами: Manual jobs + переменные пайплайна (CI/CD Variables). Можно запускать с указанием тега, ветки, окружения.

- Настройки к каждой сборке и шаблоны: include + extends в .gitlab-ci.yml. Шаблоны хранятся отдельно (например, в репозитории ci-templates), подключаются в каждый сервис.

- Секреты: Masked и Protected CI/CD Variables, либо интеграция с внешним Vault. В логах не светятся, доступ ограничивается по ролям.

- Несколько конфигураций из одного репозитория: Матричные сборки через parallel: matrix или отдельные джобы под разные окружения/архитектуры.

- Кастомные шаги: Любой shell-скрипт внутри script. Ограничений нет.

- Собственные Docker-образы для сборки: В image: указывается любой образ из своего Container Registry. Собирается через DinD (Docker-in-Docker) или Kaniko прямо в пайплайне .

- Агенты на своих серверах: GitLab Runner регистрируется на любом хосте, тегируются, и джобы распределяются по ним. Это снимает нагрузку с облачного раннера.

- Параллельность сборок и тестов: Отдельные Runner'ы с настроенным concurrent, плюс parallel в джобах тестов. Разные сервисы собираются одновременно, тесты внутри одного пайплайна идут параллельно.


GitLab закрывает почти все требования одной платформой: Git-репозитории, CI/CD, Container Registry, управление доступом, секреты, шаблоны, ручные и автоматические pipeline. Это уменьшает количество интеграций и упрощает сопровождение. Self-managed runners позволяют выполнять сборки внутри закрытой сети, получать доступ к внутренним тестовым стендам и использовать специализированные ресурсы. При росте нагрузки количество runners можно увеличивать горизонтально.

## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

----------------------------------

Я бы к этому выбрал бы ELK-стек (Elasticsearch + Logstash/Filebeat + Kibana). Классический и хорошо проверенный в продакшене стек для централизованного сбора, хранения и анализа логов.

Требования:

-Центральный сбор со всех хостов: 	Vector устанавливается на каждом Docker-хосте и отправляет данные в общий Elasticsearch

-Минимальные требования к приложениям: 	Приложение пишет лог в stdout или stderr

-Гарантированная доставка: 	Vector использует дисковый буфер, acknowledgements и повторные отправки

-Поиск и фильтрация 	Elasticsearch индексирует поля, Kibana Discover поддерживает KQL и фильтры

-Интерфейс для разработчиков:	Kibana предоставляет web-интерфейс и ролевую модель

-Ссылка на сохранённый поиск:	Discover session сохраняется как Saved Object и может быть опубликована ссылкой


Vector ест меньше ресурсов, чем тяжёлая схема с Logstash на каждом/любом сервере, умеет читать Docker логи и поддерживает дисковую буфферизацию. Elasticsearch хорошо подходит для индексирования больших объёмов журналов, а Kibana предоставляет привычный интерфейс для разработчиков, сохранённые поиски, ссылки и управление правами.

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

------------------------------------------------------------

Я выбрал бы к этому заданию Prometheus (сбор и хранение метрик) + Node Exporter (метрики хостов) + cAdvisor (метрики контейнеров) + Grafana (UI и панели) + Alertmanager (опционально, для алертов). Это стандартный cloud-native стек. Prometheus сам «вытягивает» метрики по HTTP (pull-модель), что упрощает обнаружение целей в динамической микросервисной среде.

Требования:

- Сбор метрик со всех хостов и сбор CPU/RAM/HDD/Network по хостам. На каждом хосте запускается Node Exporter. Он экспортирует метрики ядра и ОС: node_cpu_seconds_total, node_memory_MemAvailable_bytes, node_filesystem_*, node_network_* и т.д. Prometheus scrape-ит все Node Exporter-ы по service discovery .

- Метрики потребления ресурсов каждым сервисом (CPU/RAM/HDD/Network). Для контейнеров используется cAdvisor. Он собирает container_cpu_usage_seconds_total, container_memory_working_set_bytes, container_fs_*, container_network_* с разбивкой по pod/container/namespace. Prometheus забирает эти метрики с каждого узла .

- Метрики, специфичные для каждого сервиса. Каждый сервис экспортирует собственные метрики в формате Prometheus (endpoint /metrics). Это могут быть бизнес-метрики (число заказов, latency gRPC-методов, размер очереди) или технические (время ответа БД, ошибки). Prometheus scrape-ит эти endpoint-ы наряду с инфраструктурными.

- UI для запросов и агрегации. Prometheus имеет встроенный UI с PromQL, но для постоянной работы используется Grafana. В Grafana Prometheus подключается как datasource, и инженер может выполнять любые PromQL-запросы и агрегации (sum, avg, rate, histogram_quantile и т.д.) .

- UI для настройки различных панелей. Grafana позволяет создавать дашборды с панелями (графики, таблицы, singlestat, heatmap). Панели настраиваются независимо, объединяются в дашборды по сервисам или по хостам, и могут использовать переменные для переключения между сервисами/окружениями. Это закрывает требование «настраивать различные панели для отслеживания состояния системы» .



Prometheus является стандартным решением для pull-сбора метрик микросервисов. Поддерживаются labels, service discovery, PromQL и правила оповещения. Node Exporter и cAdvisor закрывают инфраструктурные метрики без изменения приложений. Grafana позволяет создавать панели для разных команд и окружений, использовать переменные и хранить Dashboard как JSON в Git.
